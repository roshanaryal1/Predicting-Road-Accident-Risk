Win thesis

Judges score impact, innovation, SDG alignment, and evidence — not code quality alone. The model already clears the technical bar (R² 0.88, 517K training rows, deployed live). What's missing is proof of real-world consequence: a quantified harm-reduction estimate, a named deployment context, and a bias/ethics accounting. Close those three gaps and this submission out-competes typical "we built a model" entries.

03

Gap-closing workstreams

A. Impact quantification (highest leverage)

A model with no stated consequence reads as an exercise. Compute and state, with method shown: given accident-density and curvature as top SHAP features, estimate injuries/fatalities avoidable if risk-scored road segments received targeted intervention (signage, lighting, speed limit review). Use published road-safety cost-per-fatality or WHO regional injury rates to translate risk-score reduction into an order-of-magnitude human/economic impact figure. Show the arithmetic — judges trust a shown estimate over an asserted one.

B. Ethics & fairness accounting

Document known limitations: geographic bias in training data (which regions/road types are over/under-represented), lack of demographic features (by design — model uses road/environment only, not driver identity), and a stated boundary of use ("decision support for infrastructure planning, not individual liability judgments"). One page, direct language, no hedging.

C. SDG narrative integration

Add an explicit SDG section to README and in-app: target numbers, one-sentence mechanism ("risk scoring → targeted infrastructure spend → fewer serious injuries"), and the §03A impact estimate. This is the single most copy-pasteable section for the application form.

D. Demo consolidation

Pick one canonical live surface for judges — the working Streamlit deployment is already live and proven; the React/FastAPI stack should be positioned as "in-progress production architecture" in the roadmap, not the thing judges are asked to click through. Splitting judge attention between two demos with different maturity levels reads as unfinished.

E. Evidence packet

Screenshot set: live gauge prediction, SHAP feature-importance chart, model comparison chart. One 60–90s screen-recording walkthrough (form allows supporting files in the zip). State the live demo URL directly in the application form text, with a one-line fallback pointer ("if the link is cold-starting, see attached recording") — closes the §06 cold-demo risk at the point a judge actually reads it, not just internally.
